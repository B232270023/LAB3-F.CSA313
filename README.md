## 1. Лабораторийн ажлын зорилго

Энэхүү лабораторийн ажлын зорилго нь системийн чанарын шаардлагыг хэмжигдэхүйц чанарын сценарио болгон тодорхойлж, тэдгээрээс SLI (Service Level Indicator), SLO (Service Level Objective) болон k6 threshold гарган туршихад оршино.

Туршилтад Node.js болон Express ашиглан локал REST API үүсгэсэн. API нь өөр өөр зан төлөвтэй дараах гурван endpoint-тэй.

* `POST /cart/add` — хурдан хариу өгөх endpoint
* `GET /report` — 200–400 ms санамсаргүй хугацааны сааталтай endpoint
* `POST /pay` — хүсэлтийн ойролцоогоор 5%-д HTTP 500 алдаа үүсгэдэг endpoint

Системийг k6 ашиглан 20 виртуал хэрэглэгчийн ачааллаар туршиж, performance, reliability болон availability чанарын үзүүлэлтүүдийг хэмжсэн.

# 3. Чанарын сценарио

## 3.1 Performance Scenario — `/cart/add`

| Хэсэг                  | Тодорхойлолт                                                                   |
| ---------------------- | ------------------------------------------------------------------------------ |
| **Тойм**               | Хэрэглэгч сагсанд бараа нэмэх үед систем хурдан хариу өгөх ёстой.              |
| **Системийн төлөв**    | Сервер хэвийн ажиллаж байгаа бөгөөд 20 виртуал хэрэглэгчийн ачаалал авч байна. |
| **Орчны төлөв**        | Локал тестийн хэвийн ачааллын орчин.                                           |
| **Гадаад өдөөлт**      | Хэрэглэгч `POST /cart/add` хүсэлт илгээнэ.                                     |
| **Шаардлагатай хариу** | Сервер хүсэлтийг амжилттай боловсруулж HTTP 200 хариу буцаана.                 |
| **Хэмжүүр**            | `/cart/add` хүсэлтийн response time-ийн p95 нь 5 ms-ээс бага байна.            |

### Тайлбар

`/cart/add` нь өгөгдлийн сан болон нэмэлт удаан боловсруулалт ашигладаггүй хурдан endpoint учраас localhost орчинд маш бага latency үзүүлэх боломжтой. Иймээс `p(95)<200ms` гэх мэт хэт сул босго ашиглахын оронд хэмжилтийн бодит үр дүнд тулгуурлан `p(95)<5ms` босгыг сонгосон.

## 3.2 Reliability Scenario — `/pay`

| Хэсэг                  | Тодорхойлолт                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Тойм**               | Хэрэглэгч төлбөр хийх үед системийн төлбөрийн endpoint-ийн алдааны давтамж зөвшөөрөгдөх хэмжээнд байх ёстой. |
| **Системийн төлөв**    | Сервер хэвийн ажиллаж, төлбөрийн хүсэлтүүдийг хүлээн авч байна.                                              |
| **Орчны төлөв**        | 20 виртуал хэрэглэгчтэй 1 минутын хэвийн ачааллын тест.                                                      |
| **Гадаад өдөөлт**      | Хэрэглэгч `POST /pay` хүсэлт илгээнэ.                                                                        |
| **Шаардлагатай хариу** | Төлбөрийн хүсэлтүүдийн дийлэнх нь амжилттай HTTP 200 хариу авах ёстой.                                       |

# 4. SLO хүснэгт

| Сценарио            | SLI                              | Threshold / SLO  | Цонх / Нөхцөл              |
| ------------------- | -------------------------------- | ---------------- | -------------------------- |
| Cart Performance    | `/cart/add` response time p95    | `p(95) < 5 ms`   | 20 VU, 1 минут             |
| Report Performance  | `/report` response time p95      | `p(95) < 450 ms` | 20 VU, 1 минут             |
| Payment Reliability | `/pay` failed request rate       | `rate < 8%`      | 20 VU, 1 минут             |
| Availability        | Successful checks / total checks | `rate > 90%`     | 20 VU, 2 минут, chaos test |

Эдгээр SLO-г `slo-test.js` файл дахь k6 threshold-уудтай ижил утгаар тодорхойлсон.

```javascript
thresholds: {
    'http_req_duration{name:cart}': ['p(95)<5'],
    'http_req_failed{name:pay}': ['rate<0.08'],
    'http_req_duration{name:report}': ['p(95)<450'],
    'checks': ['rate>0.90'],
}
```

# 5. Availability Error Budget

Availability SLO:

```text
Availability >= 90%
```

Chaos туршилтын хугацаа:

```text
2 минут = 120 секунд
```

Зөвшөөрөгдөх unavailable хувь:

```text
100% - 90% = 10%
```

Тиймээс хугацаагаар тооцсон error budget:

```text
120 секунд × 10% = 12 секунд
```

Өөрөөр хэлбэл 2 минутын туршилтын хугацаанд систем нийт **12 секунд хүртэл unavailable** байвал хугацаанд суурилсан 90%-ийн availability SLO-д багтах боломжтой.

Chaos туршилтад серверийг ойролцоогоор 10 секунд зогсоохоор төлөвлөсөн. Энэ нь хугацаагаар тооцсон 12 секундийн error budget-аас бага байна.

Гэхдээ k6-ийн `checks` хэмжүүр нь хугацааны availability биш, **хүсэлтийн амжилтын хувь** гэдгийг анхаарах шаардлагатай.

# 7. Chaos Availability Test

Chaos тестийн зорилго нь серверийн бодит тасалдал availability SLO-д хэрхэн нөлөөлөхийг шалгах явдал байв.

Тестийн хугацааг 2 минут болгон:

```bash
k6 run slo-test.js 2>&1 | tee results/chaos.txt
```

командаар тестийг ажиллуулсан.

Тест ажиллаж байх үед серверийг зогсоож, ойролцоогоор 10 секунд хүлээсний дараа:

```bash
node server.js
```

командаар дахин ажиллуулсан.

Сервер зогссон хугацаанд k6 хүсэлтүүд дээр `connection refused` алдаа бүртгэсэн.

## Chaos тестийн үр дүн

| Үзүүлэлт              |  Threshold |  Бодит үр дүн | Төлөв |
| --------------------- | ---------: | ------------: | ----- |
| Checks / Availability |    `> 90%` |    **82.43%** | FAIL  |
| `/cart/add` p95       |   `< 5 ms` | **632.86 µs** | PASS  |
| `/report` p95         | `< 450 ms` | **387.22 ms** | PASS  |
| `/pay` error rate     |     `< 8%` |    **20.32%** | FAIL  |

Chaos тестийн нийт check:

```text
checks_total      = 5772
checks_succeeded  = 4758
checks_failed     = 1014
```

Хүсэлтэд суурилсан бодит availability:

```text
Availability
= successful checks / total checks × 100

= 4758 / 5772 × 100

= 82.43%
```

Иймээс хүсэлтэд суурилсан бодит availability нь **82.43%** болсон бөгөөд 90%-ийн SLO-г хангаагүй.

# 8. Chaos тестийн шинжилгээ

Chaos тестийн үед availability threshold FAIL болсон. Хэдийгээр серверийг ойролцоогоор 10 секунд зогсоохоор төлөвлөсөн бөгөөд хугацаагаар тооцсон 12 секундийн error budget дотор байгаа боловч хүсэлтээр хэмжсэн availability 82.43% болсон.

Үүний гол шалтгаан нь k6-ийн `checks` нь **цагийн хувь биш хүсэлтийн хувь** хэмждэгтэй холбоотой. Сервер хэвийн үед `/report` хүсэлт 200–400 ms хүлээдэг. Харин сервер унтарсан үед хүсэлтүүд `connection refused` алдаагаар маш хурдан буцна. Иймээс сервер унтарсан нэг секундэд хэвийн ажиллаж байгаа нэг секундээс олон бүтэлгүй хүсэлт үүсэх боломжтой.

Тиймээс хугацаанд суурилсан:

```text
10 секунд downtime / 120 секунд
```

гэсэн ойлголт нь хүсэлтэд суурилсан availability хувьтай шууд тэнцэхгүй.

Мөн chaos тестийн үед `/pay` error rate **20.32%** болж, `<8%` reliability threshold мөн FAIL болсон. Сервер бүхэлдээ унтарсан үед `/pay` хүсэлтүүд ч амжилтгүй болсон учраас нэг серверийн эвдрэл availability болон reliability SLO-д зэрэг нөлөөлсөн.

Availability болон payment reliability-г илүү зөв тусгаарлахын тулд availability SLI-г серверийн health/uptime хэмжилтээр, харин payment reliability SLI-г сервер ажиллаж байгаа үеийн `/pay` endpoint-ийн HTTP 500 алдааны хувь дээр тусад нь хэмжиж болно.

Chaos тестийн дэлгэрэнгүй гаралт:

```text
results/chaos.txt
```

# 9. Intentional FAIL Test

k6 threshold зөрчигдөх үед тест хэрхэн FAIL болж, CI pipeline-д алдаа дамжуулахыг шалгахын тулд тусдаа:

```text
slo-test-fail.js
```

файл үүсгэсэн.

Энэ хувилбарт `/report` threshold-ийг зориудаар:

```javascript
'http_req_duration{name:report}': ['p(95)<100']
```

болгосон.

Гэтэл `/report` endpoint өөрөө 200–400 ms delay-тай учраас энэ threshold зориудаар биелэх боломжгүй.

Тестийг:

```bash
set -o pipefail
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt
code=$?
echo "exit=$code" | tee -a results/fail.txt
```

командаар ажиллуулсан.

## FAIL тестийн үр дүн

| Үзүүлэлт          |  Threshold |  Бодит үр дүн | Төлөв    |
| ----------------- | ---------: | ------------: | -------- |
| Checks            |    `> 90%` |    **98.17%** | PASS     |
| `/cart/add` p95   |   `< 5 ms` | **690.87 µs** | PASS     |
| `/report` p95     | `< 100 ms` | **388.98 ms** | **FAIL** |
| `/pay` error rate |     `< 8%` |     **5.46%** | PASS     |

k6 дараах threshold-ийг зөрчсөн:

```text
http_req_duration{name:report}
```

Учир нь:

```text
Required: p(95) < 100 ms
Actual:   p(95) = 388.98 ms
```

Тестийн exit code:

```text
exit=99
```

гарсан.

Энэ нь threshold зөрчигдсөн үед k6 тестийг амжилтгүй гэж тэмдэглэж, non-zero exit code буцааж байгааг харуулсан. CI/CD pipeline-д ийм exit code ашиглан чанарын шаардлага хангаагүй build-ийг автоматаар зогсоох боломжтой.

FAIL тестийн бүрэн гаралт:

```text
results/fail.txt
```

# 13. Дүгнэлт

Энэхүү лабораторийн ажлаар чанарын ерөнхий шаардлагыг хэмжигдэхүйц сценарио, SLI, SLO болон k6 threshold болгон хувиргах процессыг хэрэгжүүлсэн. Хамгийн чухал хэсэг нь threshold-ийг зөвхөн тестийг PASS болгох зорилгоор бус, endpoint-ийн бодит зан төлөв болон хэмжилтийн үр дүнд тулгуурлан сонгох явдал байсан. Үндсэн load тестээр `/cart/add`, `/report`, `/pay` болон нийт checks-д тавьсан бүх threshold амжилттай PASS болсон. `/cart/add` endpoint маш хурдан байсан тул 5 ms-ийн p95 босго сонгосон нь 200 ms гэх мэт хэт сул босгоос илүү утга учиртай болсон. `/pay` endpoint-ийн зориудаар үүсгэдэг ойролцоогоор 5%-ийн алдаатай харьцуулахад 8%-ийн reliability SLO нь хэвийн ажиллагааны үед хангагдсан. Chaos туршилтаар серверийг түр зогсооход хүсэлтэд суурилсан availability 82.43% болж 90%-ийн SLO-г хангаагүй бөгөөд `/pay` error rate мөн 20.32% болж reliability threshold-ийг зөрчсөн. Энэ туршилтаас хугацаанд суурилсан availability error budget болон хүсэлтэд суурилсан k6 checks нь ижил хэмжүүр биш болохыг харж болно. Intentional FAIL тестээр `/report`-ийн `p(95)<100ms` гэсэн боломжгүй threshold тавихад k6 тест FAIL болж `exit=99` буцаасан нь threshold-ийг CI/CD чанарын хаалга болгон ашиглаж болохыг харуулсан. Ийнхүү чанарын сценариог хэмжигдэхүйц SLO болгон тодорхойлж, бодит load болон failure нөхцөлөөр баталгаажуулах нь системийн чанарын шаардлагыг объектив байдлаар үнэлэхэд чухал болохыг энэхүү лабораторийн ажлаар ойлгосон.
